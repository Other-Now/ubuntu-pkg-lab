## Part 1: nano-blk-dkms

### The files in `debian/` and what each one is for

| File | Purpose |
|---|---|
| `control` | One **source** package (`nano-blk`) and two **binary** packages: `nano-blk-dkms` (Architecture: all, the module *source*) and `nano-blk-tools` (Architecture: any, the compiled `blkcheck`). Build-Depends: `debhelper-compat (= 13)` and `dh-sequence-dkms`. |
| `rules` | A makefile. `dh $@` runs the standard sequence; overrides build only `blkcheck` (a package build has **no kernel headers** and must not depend on the build machine's kernel), copy the module source into `/usr/src/nano-blk-<ver>/`, and pass the version to `dh_dkms`. |
| `nano-blk-dkms.dkms` | Becomes `/usr/src/nano-blk-<ver>/dkms.conf`. `dh_dkms -V` replaces `#MODULE_VERSION#`. `AUTOINSTALL=yes` means: rebuild whenever a new kernel is installed. |
| `changelog` | The version comes from here (0.1.0, then 0.1.1 for the 6.8 fix). The distribution field (`noble`) is what a PPA upload targets. |
| `copyright` | DEP-5 machine-readable format. lintian checks it. |
| `source/format` | `3.0 (native)`: no separate upstream tarball. Chosen because packaging and code live in one repo with no independent upstream releases. The trade-off is that every upload carries the full source and there is no patch layer; a real upstream project would use `3.0 (quilt)` with an `.orig.tar` and `debian/patches/`. |
| `tests/control` | autopkgtest (DEP-8) definition: two tests. |
| `blkcheck.8` + `nano-blk-tools.manpages` | Every binary in `/usr/sbin` needs a man page, or lintian warns. |

### The DKMS lifecycle (be able to draw this)

1. `apt install nano-blk-dkms` unpacks the source into `/usr/src/nano-blk-0.1.1/`.
2. The postinst (generated by `dh_dkms` from `/usr/lib/dkms/common.postinst`) runs
   `dkms add` and then `dkms build` + `dkms install` for each installed kernel that has headers.
3. On **every later kernel install**, `/etc/kernel/postinst.d/dkms` rebuilds the module (`AUTOINSTALL`).
4. Modules land in `/lib/modules/<kver>/updates/dkms/`; `updates/` wins over in-tree modules of the same name.
5. With Secure Boot, the module must be signed with the MOK key (the CI log shows
   `Signing module ...`). The key must be enrolled with `mokutil`, or the kernel refuses to load the module.

**Measured consequence (the main story):** when the build fails for *any* installed
kernel, the postinst exits non-zero (status 10), dpkg leaves the package
**half-configured**, and `apt install` reports an error. One broken kernel
flavour breaks installation everywhere, so DKMS packages must build on
every kernel a release ships.

### The 6.8 story, step by step

- nano_blk was written against 6.18 and uses `blk_mq_alloc_disk(set, &lim, data)`.
  The `queue_limits` argument appeared in **6.9** (commit 27e32cd23fed).
- Ubuntu 24.04 ships **6.8.0-149-generic** (GA) and **7.0.0-43-generic** (HWE).
- The CI matrix installs both header flavours and asks DKMS to build. **Before the
  fix:** 6.8 fails on amd64, arm64, ppc64el and s390x with
  `macro "blk_mq_alloc_disk" passed 3 arguments, but takes just 2`; 7.0 builds.
  riscv64's `linux-headers-generic` already points to 7.0, so it has no 6.8 flavour.
- **Fix:** `nano_blk_compat.h`. Below 6.9 it uses the 2-argument form, then applies the
  same limits with `blk_queue_logical_block_size()`, `blk_queue_max_hw_sectors()`,
  `blk_queue_max_discard_sectors()` and similar. It is selected with `LINUX_VERSION_CODE`.
- **After:** 9/9 kernel×arch builds succeed. autopkgtest in a VM running the
  stock 24.04 cloud image builds on 6.8.0-149-generic, loads the module, and
  runs blkcheck with 0 mismatches and 0 I/O errors.

Likely follow-up: *"Isn't `LINUX_VERSION_CODE` fragile on distro kernels?"* Yes.
Distros backport APIs without changing the version (RHEL is the classic case),
so checks can be wrong in either direction. Alternatives: probe with a compile
test at build time, as `conftest.sh` does in NVIDIA's/ZFS's DKMS packages, or
check a feature macro. For Ubuntu GA/HWE a version check was enough, and
the matrix proves it on both.

### The quality gates, and what each one catches

| Gate | Catches | Where |
|---|---|---|
| **lintian** `--pedantic --info --fail-on error,warning` | Policy violations: missing man page, bad copyright format, wrong Section, unversioned debhelper, … Result: **0 tags**. | `package` job |
| **sbuild** (unshare mode, fresh `mmdebstrap --variant=buildd` noble chroot) | Missing Build-Depends. The CI image has hundreds of packages installed, so a build can succeed there and fail on Launchpad. A clean chroot is what Launchpad's builders use. | `sbuild` job |
| **DKMS arch matrix** (docker `ubuntu:24.04` per arch; qemu-user for ppc64el/s390x/riscv64) | The module failing to compile against an arch's kernel headers. s390x is **big-endian**, so it is the arch most likely to expose endianness bugs (none here: the driver is byte-agnostic). | `dkms` job |
| **autopkgtest** (`-- qemu` on a stock noble cloud image) | Whether the installed package actually works on Ubuntu's own kernel, not the Azure kernel CI runs on. | `autopkgtest` job |

autopkgtest details worth knowing:
- `Restrictions: needs-root, isolation-machine, breaks-testbed`. Loading a module needs a
  real kernel (`isolation-machine`; a container would not do), and it changes the system
  (`breaks-testbed`), so the testbed is thrown away afterwards.
- `Test-Command: /usr/lib/dkms/dkms-autopkgtest` is **Canonical's generic DKMS test**
  (written by Martin Pitt). It is what Ubuntu's proposed-migration runs for every
  DKMS package against new kernels. The second test, `load-and-check`, is ours.
- The Ubuntu archive runs autopkgtests on every upload and on reverse-dependencies;
  a regression blocks migration from `-proposed` to the release pocket.

### What was not done

- **PPA upload:** needs a Launchpad account and GPG key. The procedure is in `docs/PPA.md`.
- **The module was only loaded on amd64.** Other architectures were compile-tested (DKMS build
  under qemu-user); a full VM boot per arch was not run.
- **arm64 compile ran natively** (GitHub arm64 runner); ppc64el/s390x/riscv64 ran under
  qemu-user emulation, which is why those take 18–39 s versus 1–2 s.

## Part 2: depsolve

### Debian version ordering (`debver.py`)

`[epoch:]upstream[-revision]`. Compare the epoch numerically, then upstream, then revision,
both with dpkg's `verrevcmp`: alternate non-digit and digit runs;
non-digits compare with the order **`~` < end-of-string < letters < everything else**;
digit runs compare numerically.

- `1.0~rc1 < 1.0` (tilde: pre-releases, backports `~bpo`, PPA `~ppa1`)
- `1.0 < 1.0a < 1.0+` (letters before `+`)
- `1.0+dfsg < 1.0.1` (`+` sorts before `.`)
- the revision is after the **last** `-`; a missing revision equals `0`

**Measured:** 200,000 real version pairs from noble main+universe (22,717
distinct versions), compared with `apt_pkg.version_compare`: **0 disagreements.**
The comparator from nano-sensor, written for cross-ecosystem CVE ranges,
disagrees on **5.95%**, e.g. `1.3-8build5` vs `1.3.0-3build1`. dpkg first splits off
the revision, compares upstream `1.3` with `1.3.0`, and the shorter one is
smaller (end-of-string sorts before `.`), so the result is `<`. nano-sensor ignores separators and
compares the token streams `1 3 8 build 5` and `1 3 0 build 1`; 8 > 0 gives `>`.
**Lesson:** "looks Debian-like" ordering is wrong about 6% of the time. Never hand-roll it for
a real system; use `apt_pkg` / `dpkg --compare-versions`.

### Dependency fields handled

| Field | Meaning | In depsolve |
|---|---|---|
| Depends | must be installed (configured) before this is *configured* | AND of OR-clauses |
| Pre-Depends | must be **configured** before this is even *unpacked* | same as Depends for *selection*; the difference is only in install **ordering**, which depsolve does not do |
| `a \| b` | alternatives, first is preferred | tried in order, with backtracking |
| `(>= 1.2)` etc. | versioned | `<<  <=  =  >=  >>`; the old `<` / `>` mean `<=` / `>=` |
| Provides | virtual package | unversioned Provides only satisfies **unversioned** deps; `Provides: x (= 2)` can satisfy `x (>= 2)` |
| Conflicts | can't be installed together (not even unpacked) | checked both directions, including against Provides |
| Breaks | the broken package must not be *configured* together | same as Conflicts for a fresh install set |
| Recommends | installed by default by apt | ignored, matching `--no-install-recommends` |

The **Provides + Conflicts + Replaces** idiom (e.g. every MTA provides and conflicts with
`mail-transport-agent`) means "exactly one of these". A package never conflicts with itself.

### The solver

Depth-first search over dependency clauses. A clause with only one viable option
is a forced move. A clause with several is a **choice point**: try each option
in apt's preference order, and on failure **backtrack**, discarding *everything*
chosen since.

apt's internal solver (`pkgDepCache::MarkInstall`, apt 2.8) walks in the same order, but
when a candidate's subtree fails it discards only that candidate and moves to the
next alternative. Packages already marked inside the failed subtree **stay marked**.
That one difference is the whole story of the remaining disagreement (below).

Install-set resolution is NP-complete (it encodes SAT through Depends/Conflicts), so
real solvers either use heuristics (classic apt) or a SAT/CDCL-style
solver. apt 3.0's new solver (`--solver 3.0`) backtracks; aptitude and
`dose-distcheck` are the other reference points.

### Matching apt's choices: what it took

Correctness alone is not enough to match apt. Two valid answers can differ, and the
interesting work was making depsolve choose **what apt chooses**:

1. **v1:** providers of a virtual package ordered by Priority, then name. On the random sample
   it was already identical. On the choice-heavy sample, 4 of the first 209 packages differed,
   all ties between Priority-optional providers (`www-browser`: apt picked `wslu`;
   `phpapi-20230831`: apt picked `php8.3-phpdbg`).
2. Read apt 2.8.3's `depcache.cc` `CompareProviders`. The order is protected, MA:same
   installed, already installed, same package group, Essential, Important, native arch,
   Priority, and then "unable to decide…" **`return A->ID > B->ID`**: the package
   apt's cache generator created *last* wins. IDs are assigned in first-mention order
   while `deblistparser.cc` parses stanzas: Package, then Pre-Depends, Depends, Conflicts,
   Breaks, Recommends, Suggests, Replaces, Enhances, then Provides.
3. **v2:** depsolve records the same first-mention order and uses it as the
   tie-break. 3 of 4 then matched.
4. **The 4th (`lomiri-common`)** is not an ordering problem; see the README for the
   measured numbers. apt tried `unity-control-center`, which fails in that context;
   apt dropped it but kept 39 packages it had marked inside the attempt (gnome-bluetooth,
   gstreamer plugins, GTK4, …). No dependency in the final set needs them. depsolve
   backtracks fully, so it doesn't carry them. Both answers pass the same independent
   `verify()` (every clause satisfied, no conflicts).

5. **A real bug found by the comparison.** `gdc-9-multilib` came out UNSAT, but apt installs it.
   noble's `libc6-x32` says `Conflicts: libc6-i386:x32`: an *architecture-qualified* relation
   naming the x32 build of libc6-i386. depsolve stripped every `:arch`, so it conflicted with the
   native libc6-i386. Fix: `:any`, `:native` and the native arch mean native; any other qualifier
   names a package that cannot exist on a single-arch system. Afterwards: random 500/500, choice 499/500.

### Final numbers (from `depsolve/results/SUMMARY.md`)

- random 500: **500/500** identical · choice-heavy 500: **499/500** · curated 68 big installs: **68/68**
- ablation on the choice set: priority+name order 490/500, name-only 486/500
- every differing answer, from apt or from depsolve, passes `verify()`

### What depsolve does not do (say so)

- No installed-state handling: no upgrades, removals or "keep installed" (the comparison uses an empty dpkg status)
- No pinning or apt preferences; candidate = highest version
- Single architecture (amd64 + all); `:any` qualifiers are stripped and Multi-Arch is not modelled
- No install **ordering** (what Pre-Depends really affects)
- No Recommends

## Interview questions this should let you answer

- *"Walk me through building and publishing a package to a PPA."* `debuild -S -sa`, sign,
  `dput`; Launchpad builds per arch from source; why source-only.
- *"A customer's DKMS module fails after a kernel update. How do you debug it?"* Read
  `/var/lib/dkms/<mod>/<ver>/build/make.log`, find the API change (here a function signature
  in 6.9), add a compat shim keyed on version or feature, and add the kernel to CI.
  The package is half-configured, so `dpkg --configure -a` once it's fixed.
- *"Why sbuild and not just dpkg-buildpackage?"* Clean chroot, so undeclared Build-Depends show up.
- *"How do you test on s390x without the hardware?"* qemu-user plus binfmt for builds; qemu-system
  (or Launchpad's builders, or the Ubuntu autopkgtest cloud) to run.
- *"Explain dependency resolution, and why apt sometimes installs things you didn't expect."*
  Alternatives, virtual providers, apt's tie-break rules, and no rollback in the classic
  solver (the lomiri case).
- *"Why is `1.0~rc1` less than `1.0`?"* Tilde sorts before end-of-string, so a pre-release sorts
  below the final release, and a backport (`~bpo`) below the version it came from.
